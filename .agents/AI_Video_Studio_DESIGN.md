# AI Video Studio — DESIGN.md

**Status:** Implementation-ready design-system and UX specification  
**Version:** 1.0  
**Design direction:** Light-only, minimal, premium, calm, production-focused  
**Applies to:** Dashboard, brief composer, brand kits, AI production pipeline, storyboard, timeline editor, captions, media library, avatars, B-roll, review and export.

> This is an original design system informed by the *principles* visible in the user-provided Moonshot screenshots: generous whitespace, a restrained light palette, focused progress communication and a compact top bar. Do not copy proprietary artwork, logos, page layouts or brand identity.

## 0. Non-negotiable principles

1. **Light UI everywhere.** Application chrome, dialogs, canvas surroundings, panels, popovers, onboarding and loading screens remain light. The *video content* may of course include dark scenes. Do not implement dark mode unless the project owner explicitly changes this requirement.
2. **One primary action per screen.** Secondary operations should not compete with it.
3. **Progressive disclosure.** Start with a prompt and useful presets; reveal the storyboard, timeline and expert controls when relevant.
4. **Show the work.** Display current stage, completed stages, meaningful job status, expected next step and any action required. Never invent a percent complete or ETA.
5. **Editable output.** Every AI-produced decision maps to an editable scene, asset, caption, motion component or audio track.
6. **Preserve user control.** Every generative or destructive action has a scoped preview, approval when appropriate, undo/version history and a clear account of what changed.
7. **Templates are the visual building blocks.** AI chooses/configures approved caption and motion templates; the renderer executes validated commands. New code generated by a coding agent must be reviewed and sandboxed, not executed automatically.
8. **Premium means restrained, not flashy.** Deliberate type hierarchy, generous space, precise alignment and smooth motion. Avoid neon gradients, excessive blur, decorative dashboards and competing CTAs.
9. **Accessibility is built in.** Keyboard navigation, visible focus, reduced-motion alternatives, readable contrast and accessible status announcements.
10. **Keep client brands distinct.** App UI uses its own consistent neutrals and violet accent; client colors are applied inside video templates, brand-kit previews and suitable brand-specific metadata, not across app chrome.

## 1. Experience model and navigation

### Primary navigation
- Desktop: compact 64–72px top bar with app mark/name left, centered or left-aligned project breadcrumb, contextual right actions (preview, undo/redo, export, account). No permanent giant navigation rail.
- Workspace pages: Home, Projects, Brand Kits, Assets, Templates, Jobs; use a compact project switcher or an expandable navigation menu. Show secondary navigation only when needed.
- Editor: collapsible left **Assets/Scenes** panel; large center **Preview**; optional right **Inspector**; bottom **Timeline** that may collapse. Give preview the largest share of space.
- Mobile: project review, briefs, asset upload and job monitoring are supported; advanced timeline editing can show a clear desktop-required notice instead of a broken cramped interface.

### Primary journeys
A. Brief → asset upload → AI plan → review/approve storyboard → generate assets → assemble → inspect preview → export.  
B. Upload finished footage → transcribe → choose caption style → edit transcript → review → export.  
C. Open existing project → prompt a specific edit → view proposed changes → approve → regenerate only affected portions → compare versions.

### Home page
- A single prominent heading: “What are we creating today?”
- Wide multiline prompt input; supporting controls for industry, aspect ratio, duration, brand kit and attachments.
- One primary button: **Create project**.
- Below: recent projects, continue editing, templates; no crowded hero carousel or redundant KPI cards.
- Show estimated cost before paid generation when provider prices can be calculated; otherwise clearly label an estimate or unavailable value.

Do not use violet for every text element. Important controls should remain easy to find through hierarchy, not color overload. Recheck all color combinations against WCAG 2.2 AA (4.5:1 for normal text, 3:1 for large text and required UI boundaries).

### Typography
- Preferred UI typeface: **Inter**, with system-ui fallback; use licensed or open-source fonts bundled appropriately. Do not ship downloaded commercial fonts without rights.
- Headings: 32–40px / 1.15 home hero; 24–28px / 1.2 page titles; 18–20px section titles.
- Body: 14–16px / 1.5; captions/metadata 12–13px only when comfortable and accessible.
- Weights: 400 body, 500 labels, 600 headings/buttons, 700 sparingly for hero titles.
- Use sentence case. Avoid large blocks of uppercase or gratuitous letter spacing.
- Video typography is **separate** and may use client brand fonts, editorial serifs or heavy display types.

### Spacing, dimensions and shape
- 4px base spacing scale: 4, 8, 12, 16, 20, 24, 32, 40, 48, 64, 80.
- Content max width: 1200–1320px for dashboards; prompt column 680–800px; editor fills available workspace.
- Cards: 12–16px radius; modals: 16–20px; inputs/buttons: 10–12px; pills fully rounded only for badges.
- Border: 1px neutral. Shadows: minimal, e.g. `0 6px 24px rgba(20,24,45,.06)` for floating elements, not every card.
- Desktop control height 40–44px; touch targets at least 44×44px wherever practical.
- Maintain safe areas around mobile cutouts and export CTA overlays.

## 3. Components and states

### Buttons
- Primary: filled violet, white label, one per section or modal. Disabled state must be distinguishable without being mistaken for loading.
- Secondary: white with neutral border, dark label. Tertiary: text/icon button with clear hover/focus treatment.
- Destructive: separate danger variant and confirmation where irreversible.
- Loading: retain button width, display spinner + verb (“Generating…”) and prevent duplicate submissions; provide cancel only when underlying job supports it.

### Inputs and forms
- Labels stay visible; placeholders supplement rather than replace labels.
- Brief composer uses an auto-growing textarea; attach files and choose brand/aspect/duration in a tidy utility row.
- Show validation inline with a remedy, e.g. “Upload a supported MP4 or MOV, max 2 GB,” using real limits from implementation.
- Never accept a prompt as permission to publish, overwrite approved content or spend an unbounded amount.

### Cards, thumbnails and library
- Image/video thumbnail, human-readable title, aspect ratio, duration, client and state; avoid text over a busy image without an overlay.
- Skeletons match final card dimensions and avoid layout jumps.
- Asset source badges: **Uploaded**, **AI-generated**, **Licensed**, **Approved**, **Needs review** as appropriate.
- Add provenance, provider/model, generation prompt, rights/consent and creation time in asset details, not cluttering the grid.

### Dialogs, menus and toasts
- Modals only for focused decisions; use side panels for detailed editing and full pages for complex flows.
- Confirmation dialogs explicitly name what will change and what stays preserved.
- Toasts confirm low-risk actions; errors persist within the relevant job or form until resolved.
- Tooltips explain icons but never contain information required to operate the app.

## 4. Screen-by-screen guidelines

### 4.1 Project dashboard
- Header: project name, client, current stage, preview/export action.
- Main body: most recent playable preview and “Continue from [stage]”.
- Supporting strip: storyboard, generation jobs, assets, version history.
- Never present technical job IDs as the main user-facing label.

### 4.2 Prompt/brief composer
- Centered 680–800px region with calm white space.
- Primary prompt; industry templates as optional chips: Real Estate, E-commerce, Manufacturing, Tech, Avatar, Motion Graphics.
- Controls: duration (30/60/90 sec/custom), aspect ratio (9:16/16:9/1:1/4:5), language, client brand kit, files.
- AI summarizes its understanding before expensive generation. Surface missing essential facts; do not fabricate property sizes, prices, product specifications or testimonials.

### 4.3 AI production progress
- Large central active-stage card with clear heading, plain-English description and a small source thumbnail when available.
- A vertical or horizontal stepper: Brief → Plan → Storyboard → Assets → Edit → QA → Export.
- Stage states: queued, running, awaiting approval, succeeded, failed, cancelled. Show actual per-stage counts when available (“3 of 5 scenes generated”).
- Display warnings and recovery actions (“Retry scene 4”, “Switch provider”, “Use uploaded footage”).
- Do not present decorative 0–100% progress unless measurable; no artificial countdown or invented ETA.
- Keep navigation accessible while jobs run; users may leave and return without losing state.

### 4.4 Storyboard
- Scene cards with timestamp, narrative purpose, script, shot type, source/AI asset, caption style and status.
- Allow reorder by buttons as well as drag-and-drop; scene duplication and locking.
- Approve by scene or entire storyboard. Clear revision history.
- Highlight changed scenes on regeneration; preserve approved scenes unless explicitly included in the edit.

### 4.5 Editor
- Four regions: collapsible assets/scenes left, dominant video preview center, collapsible inspector right, timeline below.
- Clear tab separation for Text, Captions, Motion, Audio, Color and Export. Avoid showing all panels simultaneously.
- Playback controls near preview; timecode and playhead always legible.
- Multi-track timeline: footage/avatars, text/motion, captions, voice, music/SFX. Visible snapping, trim handles and track lock/mute.
- Properties inspector uses task-specific fields with immediate preview, not raw JSON by default.
- Provide keyboard shortcuts plus a discoverable shortcut menu; maintain undo/redo for all editing commands.
- Store edits as typed operations with stable scene/asset IDs. Export is never the source of truth; the editable project is.

### 4.6 Caption studio
- Transcript-first workflow with word-level timing and editable text.
- Preview style thumbnails for Editorial, Dynamic, Social, Real Estate, Behind Subject and Glass UI.
- Controls: typography, highlight words, placement, animation intensity, safe area, per-scene overrides.
- Behind-subject text requires reliable segmentation/masking; show fallback foreground captions if confidence is low.
- AI suggestions should remain editable and previewable. Do not silently rewrite quoted speech or factual numbers.

### 4.7 AI editing copilot
- Dockable chat-style panel in the editor; prompt includes current project/selected scene context.
- Every request produces a *proposed change set* listing scenes/assets affected, estimated API cost, and what remains unchanged.
- Separate **Preview changes** and **Apply changes**; require approval for destructive, paid or publication actions.
- Show per-step results and partial failures; include Undo and Compare versions.
- User can say “Replace only scene 4 B-roll; preserve voice and captions” and the system must enforce the preserved fields.

### 4.8 Client brand kits
- Logo, colors, type, approved claims/CTAs, contact details, preferred video styles, voice and pronunciation dictionary.
- Validation and optional client approval status for factual claims.
- Brand color affects video exports and branded templates, not the whole application shell.

### 4.9 Export
- Simple presets: Reels/Shorts 1080×1920, YouTube 1920×1080, square 1080×1080, portrait 1080×1350, plus custom settings.
- Show frame rate, codec, expected dimensions, subtitle burn-in vs sidecar, audio loudness and file destination.
- Explain when a render is a preview vs final quality; never imply low-resolution preview is publication-ready.
- Preserve source files and editable project; final assets link back to render settings and project version.

## 5. Motion and interaction guidelines

- UI animation duration: micro-interactions ~120–180ms; panel transitions ~180–260ms; larger stage transitions ~300–450ms.
- Easing: smooth and restrained; avoid elastic, bounce and excessive parallax in workspace chrome.
- Prefer opacity/transform to layout-heavy animations; respect `prefers-reduced-motion` with instant or subtle alternatives.
- Hover is not the sole interaction cue. Focus and touch behavior must work without hover.
- Video motion graphics may be expressive, but are governed by each client’s template/creative brief and should not bleed into the application UI.

## 6. Content and microcopy

- Use direct verbs: “Generate storyboard”, “Replace B-roll”, “Review changes”, “Render preview”, “Export video”.
- Explain work in plain English: “Transcribing audio” rather than “ASR pipeline initialized”.
- Avoid vague promises: never say “Your video is ready” until the render exists and passes basic checks.
- A failure message must include what failed, impact, next step and whether the user will be charged or must retry, based on actual provider response.
- Clearly mark AI-generated people/scenes where applicable and distinguish illustrative property renders from actual property footage.

## 7. AI pipeline UX and user trust

- Step handoff cards show input → output → provider/model → version → current status.
- Each stage is independently rerunnable, with an impact preview showing downstream stages that must refresh.
- A retry must not delete earlier approved results; preserve them as versions.
- Parallel jobs display separately; do not block completed work because one optional scene failed.
- Display usage by provider and project and distinguish estimates from settled usage.
- Limit spend via configurable budgets and confirmation thresholds.
- Face/voice cloning requires affirmative authorization; store provenance and consent records with assets.
- For real estate: do not invent rooms, dimensions, views, surroundings or property attributes; label illustrative visualization and require review of public-facing factual claims.
- For e-commerce: preserve actual garment/product identity, prints, color and construction; misleading AI substitutions require rejection or clear disclosure.

## 8. Responsive and performance targets

- Breakpoints (starting points): <640px mobile, 640–1023px tablet, ≥1024px desktop; validate against real content.
- Mobile: single-column dashboard, sticky primary CTA as needed; inspect/approve projects and review videos. Avoid tiny timeline tracks.
- Tablet: two-pane storyboard and lightweight edit controls; collapsible inspector.
- Desktop: full editor, timeline and keyboard shortcuts.
- Use virtualized asset lists/timeline clips when large; generate thumbnails/proxy video for smooth editing and keep full-res originals for export.
- Defer heavy media loads outside viewport; use resumable uploads and job recovery for long tasks.
- Do not make arbitrary promises of render speed: benchmark on the actual Windows machine and target codecs.

## 9. Accessibility acceptance criteria

- WCAG 2.2 AA targets for contrast, keyboard operation and visible focus.
- All icon buttons have accessible labels; stages expose status text, not color alone.
- Progress uses accessible live-region announcements at meaningful transitions, not noisy updates every frame.
- Captions/video player support controls and transcript where applicable.
- Drag-and-drop actions have keyboard alternatives; dialogs trap focus properly and restore it upon close.
- Test at 200% zoom and with reduced motion; no clipped primary actions.

## 10. Implementation contract for Codex / coding agents

Before coding a screen:
1. Read this `DESIGN.md` and project architecture documentation.
2. Identify the screen's single primary user task and its empty/loading/error/success states.
3. Use shared components and design tokens; never invent screen-specific brand colors or a dark app shell.
4. Build the static layout and most-visible state first; then add interaction and animation.
5. Wire real state and actions. Do not ship fake functional controls or random simulated job percentages.
6. Test viewport sizes, keyboard access, focus, errors, loading, approval and cancellation.
7. Capture desktop/mobile screenshots for review and fix overflow or inconsistent spacing.
8. Verify that expensive or destructive AI changes show scope and require appropriate confirmation.

### Suggested structure

Use Tailwind CSS or CSS modules consistently; avoid mixing several visual component frameworks. A headless accessible component primitive library is acceptable if fully styled with these tokens.

## 11. Definition of done — UI/UX

A screen is done only when:
- [ ] Light-only UI, correct tokens and typography; no unapproved dark chrome.
- [ ] One obvious primary action and sensible progressive disclosure.
- [ ] Empty, loading, failed, paused/awaiting-approval and successful states are designed where relevant.
- [ ] Real stage status, no fake percentage/ETA, actionable failures.
- [ ] Accessible keyboard focus, contrast and reduced-motion support.
- [ ] Responsive layout tested at mobile, tablet and desktop widths.
- [ ] Project edits preserve versions and show affected scope.
- [ ] Real client product/property facts and consent are protected by review gates.
- [ ] Screenshots reviewed for alignment, wrapping, overflow and premium visual restraint.

## 12. What NOT to do

- No default dark mode, dark sidebar or black application background.
- No oversized permanent sidebar or five equally prominent CTAs.
- No gratuitous gradients, glows, glass everywhere, giant shadows or noisy loading animations in the app shell.
- No raw AI JSON dumped into normal user flows.
- No silent overwriting of approved scenes or hidden paid-generation retries.
- No invented completion percentages, timelines, product details or property facts.
- No one-off UI styles that drift from shared tokens.
- No generic coding-agent-made landing page aesthetic with random purple blobs.

---

**North star:** A calm, light, premium creative workspace that makes a sophisticated multi-agent video-production pipeline feel simple, transparent and controllable. The application stays visually restrained; the *videos it produces* can be cinematic and bold.


## 13. Cross-document implementation map

- `AI_Video_Studio_DESIGN.md` is the **light-only application UI/UX source of truth**: shell, tokens, typography, layout, interaction, status, accessibility and component quality.
- `AI_Video_Studio_CAPTIONS.md` is the **caption-production source of truth**: transcription, timing, typography *inside the exported video*, subject masking, safe areas, subtitle exports, caption agent contracts, tests and failure handling.
- Video content can use dark backgrounds or bold branded type; this **never** changes the light application shell requirement.
- When caption editing controls need UI styling, use `DESIGN.md`; when caption visual or speech timing rules are at issue, use `CAPTIONS.md`.
- If these documents conflict, preserve user data and approvals first, then follow the more specific specification for its respective area.

### Required handoff for coding agents

Before implementing a screen or caption feature, agents must identify its document owner, extract applicable tokens/contracts, note accessibility and error states, and provide screenshot/render-based QA. Do not treat reference screenshots as permission to copy Moonshot branding or exact proprietary designs.
